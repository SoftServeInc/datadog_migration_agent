# Architecture

## The one design decision

The OpenTelemetry Demo already ships an OpenTelemetry Collector as a subchart. This
repo does not add a second collector, a gateway tier, or a vendor agent in the app's
path. It reconfigures the collector the demo already has, and that collector is the
single fan-out point.

```
                         ┌──────────────────────────────────────┐
  demo services  ───────►│                                      ├──► datadog exporter
  k6 load generator ────►│   otel-collector (DaemonSet)         │
  agent / chatbot / mcp ►│                                      ├──► otlphttp  → Splunk O11y APM
  filelog (pod logs) ───►│   presets: hostMetrics,              │    signalfx  → Splunk O11y IM
  kubeletstats ─────────►│     kubeletMetrics, clusterMetrics,  │
  k8s_cluster ──────────►│     kubernetesAttributes,            ├──► splunk_hec → Splunk Enterprise
  k8sobjects (events) ──►│     logsCollection                   │
                         │                                      ├──► otlphttp  → Splunk Agent
                         └──────────────────────────────────────┘         Observability (GenAI only)
```

Why not a gateway collector in front of the vendors? On a single-node demo cluster it
buys nothing and costs a hop, a deployment and ~300 MiB. On a real cluster you would
add one; the exporter blocks in `.render/demo-values.yaml` move across unchanged.

Why not send app telemetry through vendor agents? Because then each backend sees
telemetry shaped by a different agent, and the demo stops being a fair comparison.
Here every backend receives the same spans, from the same collector, with the same
resource attributes.

There are no vendor agents at all. The vendor-specific content that normally justifies
one — Splunk's Kubernetes navigator in particular — is reproduced by configuring the
upstream receivers the way the vendor distribution does. See *Splunk-shaped Kubernetes
telemetry* below. The known exception is Datadog's live-container and process views,
which depend on the Datadog agent's own collection path and are not available here.

## Pipelines

Generated by [scripts/render.sh](../scripts/render.sh) into `.render/demo-values.yaml`.
Read that file — it is the real answer. What follows is why.

### traces

```
processors: memory_limiter, resourcedetection, resource,
            resource/deployment_env, transform/sanitize_spans,
            gen_ai_normalizer, batch
```

- **`transform/sanitize_spans`** is upstream's processor for collapsing high-cardinality
  span names (`/api/products/1YMWWN1N4O` → `/api/products/{productId}`). Upstream's
  `values.yaml` currently lists `transform/sanitize_logs` in the traces pipeline, which
  only defines `log_statements` and is therefore a no-op for spans. We use the span one.
  This matters commercially: unbounded span names inflate custom-metric cardinality in
  both Datadog and Splunk APM.
- **`gen_ai_normalizer`** is upstream's processor that rewrites the Traceloop /
  OpenLLMetry attributes emitted by the agent, chatbot and MCP services into
  OpenTelemetry GenAI semantic conventions. It is what makes the Splunk Agent
  Observability branch work, and it also improves the GenAI views in Datadog.
- **`resource/deployment_env`** stamps both `deployment.environment` and
  `deployment.environment.name` from `DEPLOYMENT_ENVIRONMENT`. Splunk APM's environment
  selector and Datadog's `env` tag both derive from these; without them, services land
  in "unknown" and comparisons get confusing.
- **`span_metrics`** stays in the exporter list unconditionally. It is a connector that
  feeds the metrics pipeline; dropping it breaks that pipeline.

### metrics

Receivers are the upstream set (`otlp`, `kafkametrics`, `span_metrics`, `prometheus/ad`)
plus, when Datadog is on, `datadog/connector`.

`datadog/connector` is not optional for a usable Datadog demo. Without it, traces arrive
but the APM *Services* page — hits, errors, p95 — stays empty, because Datadog expects
APM stats to be computed upstream rather than derived from raw spans.

### logs

Container logs come from the `logsCollection` preset (`filelog`). Kubernetes events come
from a hand-wired `k8sobjects` receiver: the chart's `presets.kubernetesEvents` flag is
only applied in `deployment` and `statefulset` mode and is **silently ignored** for a
DaemonSet collector, so setting it would have looked correct and collected nothing. The
matching `events` RBAC rule is appended via `clusterRole.rules`. Both signals go to
Datadog and Splunk Enterprise.

**Logs are deliberately not sent to Splunk Observability Cloud directly.** Splunk's
supported path is Log Observer Connect reading from the Splunk platform, which is where
the HEC exporter is already putting them. Sending them twice would double-bill you.

### Splunk-shaped Kubernetes telemetry

Splunk's Kubernetes navigator, and APM → Related Content → Kubernetes, need more than
"some k8s metrics arrived". The receivers are configured the way Splunk's own
distribution configures them:

| Setting | Why |
|---|---|
| `k8s_cluster.metadata_exporters: [signalfx]` | Publishes Kubernetes object metadata — labels, properties, workload relationships — as Splunk dimension properties. **This is the one that matters.** Without it you get metric series with no topology to navigate or correlate against. |
| `k8s.node.condition`, `k8s.pod.status_reason`, `k8s.container.status.reason` | Off by default upstream; the navigator charts them. |
| `k8s.pod.qos_class`, `k8s.kubelet.version`, `k8s.hpa.scaletargetref.*` | Resource attributes the navigator groups by. |
| `kubeletstats.extra_metadata_labels: [container.id]` | Lets Splunk tie a container metric back to a trace. |
| `signalfx.root_path: /hostfs` | Host properties (OS, kernel, cores), so nodes are first-class objects rather than bare series. Reads the volume the `hostMetrics` preset already mounts. |
| `k8s.cluster.name` | The join key between APM spans and infrastructure. Nothing in the Kubernetes API carries a cluster name, so it must be asserted — see `resource/deployment_env`. |

The Splunk distribution splits this across two collectors, an agent and a cluster
receiver, and sets `disable_default_translation_rules: true` on the latter. That split is
not needed here. The signalfx exporter's
[default translation rules](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/exporter/signalfxexporter/internal/translation/default_translation_rules.yaml)
only rewrite `system.*`, `cpu.*`, `memory.*` and legacy container metric names — **no rule
touches `k8s.*`** — so they are a no-op on cluster metrics. The distro disables them
because it runs two processes, not because one process would be wrong.

## How destinations get switched on and off

`scripts/render.sh` reads `.env` and builds the exporter lists in bash before writing
YAML. A destination with no credentials contributes no exporter and no pipeline entry.

One subtlety worth knowing: the demo's `otlp_grpc/jaeger`, `otlp_http/prometheus` and
`opensearch` exporters stay *defined* in the merged collector config even when
`KEEP_LOCAL_BACKENDS=false`, because Helm
[cannot null out a subchart's default values](https://github.com/helm/helm/pull/12879).
They are simply referenced by no pipeline. The Collector only instantiates components a
pipeline references, so they are never built and never dial anything. `helm template`
output will still show them; that is expected.

## Credentials

One Kubernetes Secret, `otel-demo-destinations`, created by `scripts/deploy.sh` from
`.env`. The collector references it through `extraEnvs` → `secretKeyRef`, and the
collector config uses `${env:VAR}`. No token is ever written into a values file.

## Resource footprint

| | approx. memory |
|---|---|
| Demo services + Kafka + Postgres + Valkey | ~4.5 GiB |
| Collector | 800 MiB limit |
| Bundled Jaeger + Prometheus + Grafana + OpenSearch | ~3 GiB |

On macOS and Windows all of this lives inside the podman machine, so the machine has to
be at least `CLUSTER_MEMORY_MB` + 2 GiB. `scripts/engine.sh` checks and offers to grow it.

`KEEP_LOCAL_BACKENDS=false` (the default) drops the bundled backends. Turn them back on
when you want to confirm that telemetry exists at all before blaming a vendor.

## Known sharp edges

- **Multi-node clusters.** The collector is a DaemonSet, and `k8s_cluster` and
  `k8sobjects` are cluster-scoped. `clusterMetrics` sets up leader election on its own;
  the hand-wired `k8sobjects` receiver does not, so on more than one node you get one
  copy of Kubernetes events per node. `scripts/cluster.sh` warns about this. The fix is a second
  collector in `deployment` mode owning the cluster-scoped receivers; out of scope for a
  single-node demo, but a real consideration before pointing this at a shared cluster.
- **Pinned versions.** [versions.env](../versions.env) pins all three charts. The
  pipeline overrides replicate upstream processor lists, so a chart bump can silently
  drop a processor upstream added. Re-read `.render/demo-values.yaml` after bumping.
- **`USE_VCR=True`.** The demo's agent replays recorded LLM responses. GenAI spans are
  real spans with real attributes, but token counts and latencies are from the cassette,
  not from a live model.
